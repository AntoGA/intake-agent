# Агент обработки заявок для cc-c.ru

Пакет для публикации страницы продукта и запуска закрытого пилота. Сайт, почта и Telegram поступают в общую очередь. Агент подготавливает черновик, сотрудник согласует его. Отправки клиентам нет.

## Что входит

- `public/`: адаптивная страница продукта, локальное интерактивное демо и презентация.
- `core.py`, `adapters.py`, `app.py`: очередь SQLite, приём источников, черновики и API согласования.
- `compose.yaml`: два контейнера с непривилегированным пользователем. API доступен на 127.0.0.1:8010.
- `deploy/nginx-location.conf`: фрагмент для существующего HTTPS-сайта.
- `scripts/`: проверка пакета, генерация конфигурации и резервное копирование.
- `.github/workflows/ci.yml`: тесты, проверка JS и сборка Docker в GitHub Actions.

## Статус

Это пилот, а не законченная система продаж. Демо страницы работает целиком в браузере и явно обозначено как имитация. Backend по умолчанию использует фиксированный ответ. Реальная модель, почта и Telegram требуют настройки. Вложения и голос не анализируются. Автоматическое объединение клиентов между каналами отсутствует. Админ-панель, CRM и отправка сообщений не реализованы.

Страница подготовлена для `https://cc-c.ru/projects/intake-agent/`. Адрес предлагаемый, страница пока не опубликована. Текущие исходники и CSS основного сайта недоступны, поэтому оформление отдельной страницы основано на презентации. Навигацию основного сайта и фирменный значок следует подключить в его исходном проекте после получения доступа.

## Публикация страницы

На сервере с существующим cc-c.ru:

1. Разместите этот проект в `/opt/cc-intake-agent`. Не копируйте его целиком в публичный каталог.
2. Создайте новый каталог страницы и скопируйте только публичные файлы:

```bash
sudo install -d -m 755 /var/www/cc-intake-agent-public
sudo cp public/index.html public/style.css public/demo.js public/product.pptx /var/www/cc-intake-agent-public/
sudo chmod 644 /var/www/cc-intake-agent-public/*
```

3. Сохраните резервную копию действующего файла Nginx для cc-c.ru. Добавьте содержимое `deploy/nginx-location.conf` внутрь его HTTPS `server {}`. Это фрагмент, не полный конфиг. Оставьте существующие CSP, TLS, маршрут /api/contact и прокси Next.js на 3001.
4. Проверьте, что ваша CSP разрешает внешние JS/CSS с собственного домена. В странице нет inline-скриптов, сторонних шрифтов и сетевых запросов демо. Если текущая CSP разрешает только nonce, потребуется отдельное согласованное правило для статической страницы. Не отключайте CSP на всём сайте.
5. Проверьте конфигурацию и только затем выполните reload:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

6. Проверьте предложенный URL, мобильную ширину, сценарий сбоя и загрузку презентации. Если меняете URL, обновите canonical и og:url в index.html.
7. Добавьте ссылку «Агент обработки заявок» в раздел проектов основного сайта. Исходники Next.js в этот пакет не входят.

Страница работает без backend. Не создавайте публичный proxy_pass к 8010 для демонстрации.

## Закрытый backend

Требуется Docker с Compose. Свободность 8010 нужно проверить на сервере, например `ss -ltn`. Проект не меняет службу `cc-c-v3.service`.

```bash
cd /opt/cc-intake-agent
python3 scripts/init_env.py
sudo install -d -m 700 -o 10001 -g 10001 data
docker compose config --quiet
docker compose up --build -d
curl --fail http://127.0.0.1:8010/health
```

Для частного доступа с компьютера: `ssh -L 8010:127.0.0.1:8010 пользователь@сервер`.

ADMIN_TOKEN разрешает чтение и согласование. INGEST_TOKEN разрешает только приём. Оба задаются в `.env`, генерируются отдельно, не публикуются и не попадают в браузерный код. Документация API `/docs` отключена.

## Подключение источников

**Форма.** Сервер сайта вызывает POST `http://127.0.0.1:8010/api/form` с `Authorization: Bearer <INGEST_TOKEN>`:

```json
{"external_id":"стабильный-id-заявки","contact":"client@example.org","text":"Содержание заявки"}
```

На стороне существующего сайта нужна надёжная очередь отправки: сохраняйте заявку и её ID перед вызовом, повторяйте неуспешные доставки с тем же ID. Не заменяйте отправку почты в /api/contact и не делайте необязательный fire-and-forget без сохранения. Точная вставка зависит от актуального серверного обработчика, которого в этом пакете нет.

**Почта.** В `.env` заполните IMAP_HOST, IMAP_USER, IMAP_PASSWORD (пароль приложения), IMAP_FOLDER. Выделите папку Leads. Первый запуск прочитает все письма этой папки. Адаптер читает через TLS и BODY.PEEK. Настройки провайдера нужно проверить отдельно. Данные From не доказывают личность клиента.

**Telegram.** Заполните TELEGRAM_BOT_TOKEN для отдельного бота. Используется getUpdates, активный webhook или второй потребитель не допускаются. Читаются личные сообщения боту, не личные переписки владельца.

**Модель.** Заполните context.md утверждёнными правилами. Укажите AI_MODE=live, LLM_ENDPOINT (полный HTTPS endpoint совместимого chat/completions API), LLM_MODEL, LLM_API_KEY. Совместимость провайдера требует проверки. Текст заявки передаётся провайдеру. Контакт отдельно не добавляется в запрос модели, но может содержаться в тексте заявки. Модель не получает инструменты или доступ к токенам. Сотрудник проверяет каждый черновик.

После настройки: `docker compose up --build -d --force-recreate`. Используйте ровно один worker. Он периодически проверяет оба источника и очередь. Для большей нагрузки потребуются отдельные рабочие процессы и новая схема блокировок.

## Управление и восстановление

С ADMIN_TOKEN:

- GET /api/leads: последние 200 заявок.
- GET /api/leads/{id}/events: история.
- POST /api/leads/{id}/approve: согласовать готовый черновик, без отправки.

Обычная последовательность: queued, processing, review, approved. Ошибка запускает отложенный повтор. После трёх неудачных попыток статус manual. Прерванная обработка старше пяти минут возобновляется. Повторная доставка одного идентификатора не создаёт дубль. Другие данные с тем же ID дают конфликт. Система пока не предоставляет UI для исправлений или повторного запуска manual.

Резервная копия: `sudo python3 scripts/backup.py data/intake.db /защищённый/каталог/intake-backup.db`. Не храните копии в Git или public. Для восстановления остановите контейнеры, сохраните текущую базу, восстановите копию в чистый каталог data с владельцем 10001:10001. Старые WAL/SHM нельзя смешивать с другой базой. Затем запустите контейнеры. Определите срок хранения и удаления заявок до приёма рабочих данных.

## Проверки

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m unittest discover -v
.venv/bin/python scripts/check_release.py
node --check public/demo.js
```

Локально проверяются ядро, разделение токенов, согласование, ограничения размера, конфликты ID и границы публичного пакета. Браузерная проверка, Docker, Nginx и реальные интеграции требуют целевой среды. CI включает сборку Docker, но его успешность можно подтвердить только после запуска в репозитории.

```bash
git clone https://github.com/AntoGA/intake-agent.git
cd intake-agent
```

Перед изменениями создавайте отдельную ветку и PR. `.env`, базы данных и резервные копии исключены из Git. Лицензия на публичное использование пока не назначена владельцем.

## Откат публикации

Удалите только добавленные location для проекта, выполните nginx -t, затем reload. Основной Next.js-сайт продолжит работать по существующему маршруту. `docker compose stop` остановит пилот с сохранением данных. Перед обновлением страницы сохраните копию её публичного каталога. Новые версии backend проверяйте на копии БД до замены.
